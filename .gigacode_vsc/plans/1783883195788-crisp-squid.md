# План новой архитектуры семантического слоя для dbt-clickhouse-lab

## Текущее состояние

### Проблемы существующей архитектуры

1. **Дублирование измерений** между `dimensions.yml` и `semantic_models.yml`
   - Измерения определены дважды с разными именами и описаниями
   - Сложные ссылки между файлами (например, `order_status_dim` ссылается на `order_status` в `orders_analysis`)

2. **Неиспользуемый semantic layer**
   - Модель `f_orders_stats.sql` содержит только `SELECT 1`
   - Отсутствуют метрики для большинства бизнес-показателей
   - Не используются современные возможности dbt Semantic Layer

3. **Гибридная архитектура**
   - Data Vault (для историзации и аудита)
   - Star Schema (для производительности отчетов)
   - Semantic Layer (для BI инструментов)

## Концепция новой архитектуры

### Целевая модель: Single Source of Truth

```
┌─────────────────────────────────────────────────────────────────────┐
│                    BI Layer (Tableau/Metabase)                      │
│                    Uses dbt Semantic Layer                          │
└─────────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────────┐
│              Semantic Layer (single source of truth)                │
│                    metrics.yml + semantic_models.yml                │
│  - Unified definitions                                              │
│  - Consistent naming                                                │
│  - Centralized documentation                                        │
└─────────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────────┐
│                      Data Mart Layer                                │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  f_orders_stats (aggregated, optimized for reporting)         │  │
│  │  f_lineorder_flat_dv (wide table, DV-based)                   │  │
│  └───────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────────┐
│                  Core Data Store (Data Vault 2.0)                   │
│  Hubs (business keys)                                               │
│  Links (relationships)                                              │
│  Satellites (history + attributes)                                  │
└─────────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────────┐
│                        Staging Layer                                │
│  stg_orders, stg_customer, stg_part, stg_supplier, stg_lineitem    │
└─────────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────────┐
│                     Source Layer (S3/TPCH)                          │
└─────────────────────────────────────────────────────────────────────┘
```

### Принципы построения новой архитектуры

1. **Единая точка правды для измерений**
   - Все измерения определяются один раз в `semantic_models.yml`
   - `dimensions.yml` либо удаляется, либо используется только для aliasов

2. **Метрики как first-class citizens**
   - Все бизнес-метрики определены в `metrics.yml`
   - Метрики используют sematic models как источники
   - Автоматическая инкапсуляция логики вычислений

3. **Наследование и переиспользование**
   - Общие измерения определяются один раз и переиспользуются
   - Иерархии используют встроенные возможности dbt

4. **Поддержка времени**
   - Базовая гранулярность: день
   - Временные измерения из единого календаря

## Детальный план реализации

### Фаза 1: Унификация semantic models (1 неделя)

#### 1.1. Создать единую модель календаря

**Текущее состояние:**
- `dim_calendar.sql` содержит измерения времени
- Используется в `orders_analysis` и `lineitem_details`

**Целевое состояние:**
- Создать `calendar` semantic model в `semantic_models.yml`
- Все временные измерения определяются один раз

**Реализация:**
```yaml
- name: calendar
  model: ref('dim_calendar')
  defaults:
    agg_time: date_day
  dimensions:
    - name: date_day
      expr: date_day
      type: time
      type_params:
        time_granularity: day
    
    - name: year
      expr: year
      type: time
      type_params:
        time_granularity: year
    
    # ... остальные временные измерения
```

#### 1.2. Упростить orders_analysis

**Текущее состояние:**
- `orders_analysis` содержит базовые измерения заказов
- Используется `f_orders_stats_dv` как модель

**Целевое состояние:**
- Убрать агрегированные меры (num_orders, revenue и т.д.)
- Оставить только детальные измерения
- Использовать `sat_order_details` как модель

**Реализация:**
```yaml
- name: orders_analysis
  model: ref('sat_order_details')
  defaults:
    agg_time: O_ORDERDATE
  dimensions:
    - name: order_date
      expr: O_ORDERDATE
      type: time
      type_params:
        time_granularity: day
    
    - name: order_status
      expr: O_ORDERSTATUS
      type: categorical
    
    # ... остальные детальные измерения
```

#### 1.3. Упростить lineitem_details

**Текущее состояние:**

**Целевое состояние:**

### Фаза 4: Создать витрины данных (1 неделя)

#### 4.1. Обновить f_orders_stats

**Текущее состояние:**
- Содержит только `SELECT 1`

**Целевое состояние:**
- Агрегированная витрина по заказам
- Используется для быстрых отчетов

**Реализация:**
```sql
SELECT
    toYear(o.O_ORDERDATE) AS order_year,
    o.O_ORDERSTATUS AS order_status,
    o.O_ORDERPRIORITY AS order_priority,
    COUNT(DISTINCT o.O_ORDERKEY) AS num_orders,
    COUNT(DISTINCT c.C_CUSTKEY) AS num_customers,
    SUM(l.L_EXTENDEDPRICE * (1 - l.L_DISCOUNT)) AS revenue
FROM {{ ref('sat_order_details') }} o
JOIN {{ ref('link_order_customer') }} oc ON o.ORDER_HK = oc.ORDER_HK
JOIN {{ ref('sat_customer_details') }} c ON oc.CUSTOMER_HK = c.CUSTOMER_HK
JOIN {{ ref('link_order_lineitem') }} ll ON o.ORDER_HK = ll.ORDER_HK
JOIN {{ ref('sat_lineitem_details') }} l ON ll.ORDER_LINEITEM_HK = l.ORDER_LINEITEM_HK
GROUP BY
    toYear(o.O_ORDERDATE),
    o.O_ORDERSTATUS,
    o.O_ORDERPRIORITY
```

## Выгода от новой архитектуры

### Для бизнеса:
1. **Единый словарь данных** - все метрики и измерения определены один раз
2. **Прозрачность** - каждый может понять, как рассчитываются показатели
3. **Консистентность** - одни и те же метрики используются во всех отчетах

### Для аналитиков:
1. **Быстрая разработка** - не нужно писать SQL для простых метрик
2. **Доверие к данным** - единая точка правды
3. **Самообслуживание** - BI инструменты могут автоматическиDiscover метрики

### Для инженеров:
1. **Упрощенная поддержка** - изменения в одной точке
2. **Тестируемость** - метрики можно тестировать отдельно
3. **Масштабируемость** - легко добавлять новые метрики

## Риски и mitigation

### Риск 1: Ломаем существующие отчеты

**Mitigation:**
- Сохранить legacy витрины с суффиксом `_legacy`
- Добавить миграционный период
- Провести full testing

### Риск 2: Снижение производительности

**Mitigation:**
- Использовать агрегированные витрины для частых запросов
- Кэшировать результаты вычислений
- Оптимизировать SQL выражения

### Риск 3: Сложность миграции

**Mitigation:**
- Провести миграцию поэтапно
- Поддерживать обратную совместимость
- Документировать каждый шаг
