# Project Documentation Plan: dbt-clickhouse-lab

## Overview

This project is a Data Warehouse (DWH) implementation using ClickHouse as the database and dbt (data build tool) for data transformation. The architecture implements a hybrid approach combining Data Vault 2.0 methodology with traditional data marts, optimized for analytical workloads.

### Data Flow

1. **Source Layer**: Raw data from S3 (TPC-H dataset)
   - External tables created via `init_s3_sources` macro
   - Format: `CustomSeparated` with pipe delimiter
   - Storage: Yandex Cloud Storage

2. **Staging Layer**: Transformation and cleaning
   - Raw data extraction and normalization
   - Basic transformations and type casting
   - Preparation for Data Vault loading

3. **Data Vault Layer**: Core data storage
   - **Hubs**: Store business keys (customer, order, part, supplier)
   - **Links**: Store relationships between hubs (order-customer, order-lineitem)
   - **Satellites**: Store descriptive attributes with history tracking
   - Uses hash keys for integrity and history tracking

4. **Data Mart Layer**: Reporting optimization
   - Aggregated views for business analytics
   - Wide tables for fast querying
   - Backward compatibility views (`*_dv`)

5. **Semantic Layer**: Business abstraction
   - Unified metric definitions
   - Semantic models for BI tools
   - Business glossary and metadata

## Data Vault 2.0 Implementation

**Components**:

| Component | Description | Files |
|-----------|-------------|-------|
| **Hubs** | Business keys storage | `hub_customer`, `hub_order`, `hub_part`, `hub_supplier` |
| **Links** | Relationships between hubs | `link_order_customer`, `link_order_lineitem` |
| **Satellites** | History + attributes | `sat_customer_details`, `sat_order_details`, etc. |

**Hash Keys**:
- Hub HK: `MD5(business_key)`
- Link HK: `MD5(hub1_hk || '-' || hub2_hk)`
- Hashdiff: `MD5(attribute1 || attribute2 || ...)`

**Loading Process**:
- `LOAD_DATE`: Timestamp when data was loaded
- `SOURCE`: Indicator ('TPCH')
- `HASHDIFF`: Change detection

## Основные недостатки проекта

### 1. Неполная реализация Data Vault 2.0

**Проблема**: Модели Data Vault не соответствуют стандарту 2.0 в ключевых аспектах.

**Особенности**:
- **Отсутствует историзация**: Все satellite модели используют `now()` в качестве LOAD_DATE, что не позволяет отслеживать изменения со временем
- **Нет поддержки SCD (Slowly Changing Dimensions)**: Отсутствует механизм обновления исторических записей
- **Неполные хеш-ключи**: Link модели не хранят все связи (например, link_order_lineitem не содержит PART_HK и SUPPLIER_HK для прямых ссылок)
- **Нет обработки дубликатов**: Использование `DISTINCT` в satellite моделях маскирует дубликаты данных

**Файлы с проблемами**:
- `models/dv/sat/sat_*.sql` — все модели используют `now()` вместо временной метки из источника
- `models/dv/link/link_order_lineitem.sql` — не содержит PART_HK и SUPPLIER_HK в order_by

### 2. Неэффективная реализация semantic models

**Проблема**: Модель `v_lineitem_details_extended.sql` создает view поверх Data Vault с множеством JOINs.

**Особенности**:
- **Плохая производительность**: При каждом запросе к semantic model выполняются JOINы нескольких satellite таблиц
- **Нарушение архитектуры**:Semantic layer должен быть на вершине, а не строиться поверх Data Vault через view
- **Отсутствие кэширования**: Все JOINs выполняются на лету без материализации

**Рекомендации**:
- Материализовать `v_lineitem_details_extended` как table или view с кэшированием
- Или использовать предварительно агрегированные данные из Data Mart

### 3. Отсутствие unit-тестов для Data Vault

**Проблема**: Хотя тесты существуют, они охватывают только базовую валидацию.

**Особенности**:
- **Нет тестов историзации**: Нет проверок на корректность LOAD_DATE иHASHDIFF
- **Нет тестов целостности**: Отсутствуют тесты на непротиворечивость связей между hub-link-satellite
- **Нет тестов бизнес-правил**: Не проверяются корректность хеш-ключей и соответствие Data Vault стандарту

**Файлы с тестами**:
- `tests/dv_*.sql` — базовые тесты, не охватывают все сценарии

### 4. Неполная документация

**Проблема**: Документация неполна и не соответствует уровню сложности архитектуры.

**Особенности**:
- **Отсутствуют документы по моделям**: Нет описания для hub, link и satellite моделей в `models/` папке
- **Нет README для Data Vault**: В папке `docs/` нет документа, объясняющего Data Vault архитектуру
- **Нет SLD (Source Lineage Diagram)**: Не документировано откуда берутся данные на каждом слое

### 5. Отсутствие материализации Data Marts

**Проблема**: Data Mart слой не оптимизирован для BI-систем.

**Особенности**:
- **Нет материализованных представлений**: Для ускорения запросов к витринам должны использоваться materialized views
- **Отсутствует материализованная таблица для `f_lineorder_flat_dv`**: Было бы полезно для часто используемых запросов
- **Нет партиционирования для Data Marts**: Модели не используют оптимальное партиционирование для аналитики

### 6. Проблемы с управлением зависимостями

**Проблема**: Зависимости между моделями могут быть неявными.

**Особенности**:
- **Отсутствует dbt_relationships**: В `dbt_project.yml` не настроены проверки целостности
- **Нет явных зависимостей в моделях**: Некоторые зависимости формируются через `ref()` неявно
- **Нет контроля версий моделей**: Нет механизма отслеживания версий Data Vault моделей

### 7. Недостаточная автоматизация

**Проблема**: CI/CD и процессы развертывания можно улучшить.

**Особенности**:
- **Нет тестирования локально**: Нет команд для тестирования перед коммитом
- **Нет валидации semantic layer**: Нет шага в CI для проверки корректности `metrics.yml` и `semantic_models.yml`
- **Отсутствует линтер для YAML**: Нет проверки синтаксиса конфигурационных файлов

### 8. Проблемы с производительностью

**Проблема**: Некоторые модели могут вызывать проблемы при росте данных.

**Особенности**:
- **Нет компакции данных**: В ClickHouse не настроена компакция (MERGE) для satellite таблиц
- **Отсутствует индексация по HASHDIFF**: Потеря производительности при фильтрации по истории
- **Нет оптимизации JOINs**: В `v_lineitem_details_extended` выполнены избыточные JOINы

### 9. Отсутствие data governance

**Проблема**: В проекте не реализованы механизмы управления данными.

**Особенности**:
- **Нет метаданных о владельцах**: В моделях нет информации о владельцах данных
- **Нет уровня доступа**: Отсутствует система контроля доступа к данным
- **Нет аудита**: Нет логирования изменений данных

### 10. Ограниченная расширяемость

**Проблема**: Сложно добавлять новые источники данных.

**Особенности**:
- **Жестко заданные источники**: Структура не предусматривает добавление новых источников без изменения нескольких файлов
- **Нет универсальных макросов**: Нет шаблонов для загрузки новых источников
- **Отсутствует data contracts**: Нет контрактов на формат входных данных
