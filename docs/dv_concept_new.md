# Гибридная архитектура DWH: Data Vault 2.0 + Data Marts

## Введение

Корпоративное хранилище данных (Data Warehouse, DWH) представляет собой централизованную информационную систему, предназначенную для сбора, интеграции, хранения и анализа данных из множества разрозненных источников. В отличие от операционных баз данных (OLTP), ориентированных на быструю обработку транзакций, DWH оптимизировано для выполнения сложных аналитических запросов, построения отчетности и поддержки принятия управленческих решений.

Эффективность работы такого хранилища напрямую зависит от его архитектуры и строгого разделения на логические слои. Слоистая структура позволяет упорядочить движение данных, обеспечить их качество, консистентность и доступность для конечных пользователей.

**Гибридная архитектура** — современный подход, сочетающий преимущества Data Vault 2.0 и традиционных витрин данных (Data Marts):

- **Data Vault 2.0** обеспечивает историзацию, целостность и гибкость — данные хранятся в нормализованном виде с фиксацией изменений во времени (Slowly Changing Dimensions, SCD)
- **Data Marts / Reporting Layer** обеспечивают производительность и удобство для аналитики — данные денормализованы и подготовлены под конкретные бизнес-задачи

В гибридной архитектуре Data Vault выступает в роли **якоря данных** (Single Source of Truth), а витрины — как **оптимизированные представления** для финального потребления.

**Практический пример:** проект dbt-clickhouse-lab реализует гибридную архитектуру, где:

```
Source Layer → Staging → Core Data Store (Data Vault 2.0) → Data Marts → Reporting Layer (TPC-H) → BI
```

- **Data Vault** содержит hub, link и satellite модели
- **TPC-H** строится поверх Data Vault как финальная витрина для аналитики

---

## 1. Слой источников данных (Data Source Layer, DS)

Это начальный уровень архитектуры, представляющий собой совокупность всех систем, из которых извлекается информация. В современных организациях данные генерируются в огромном количестве и хранятся в различных форматах и системах.

**Функции:**

- генерация первичных данных. На этом этапе данные существуют в «сыром» виде, специфичном для каждой конкретной системы;
- состав: К источникам относятся транзакционные базы данных (ERP, CRM), биллинговые системы, веб-сервисы, файлы (CSV, Excel), логи приложений и внешние API;
- особенности. Данные в этом слое часто несогласованны: разные системы могут использовать разные форматы дат, валюты или идентификаторы клиентов. Задача DWH — собрать эту информацию воедино и привести к единому стандарту.

---

## 2. Промежуточный слой (Staging Area / ODS)

После извлечения данные попадают в промежуточную зону, часто называемую Staging Area или Operational Data Store (ODS). Этот слой служит буфером между источниками и основным ядром хранилища.

**Функции:**

- временное хранение: Сохранение данных до момента их полной обработки;
- очистка (Data Cleansing): Удаление дубликатов, исправление ошибок, приведение форматов к единому виду;
- логирование: Фиксация времени загрузки и метаданных о происхождении данных (Data Lineage);
- минимальная трансформация: Здесь выполняются только базовые преобразования, чтобы не перегружать систему сложными вычислениями на ранних этапах;
- важность: Наличие этого слоя критически важно для обеспечения отказоустойчивости. Если процесс загрузки в ядро прервется, данные останутся в Staging Area и не потеряются.

---

## 3. Слой хранения данных (Core Data Store / EDW)

Ядро (часто называемое Enterprise Data Warehouse — EDW) является центральным звеном всей архитектуры. Здесь происходит глубокая интеграция данных из промежуточного слоя.

**Функции:**

- интеграция. Объединение данных из разных источников в единую модель;
- историзация. Хранение истории изменений с использованием механизмов Slowly Changing Dimensions (SCD). Это позволяет анализировать данные не только на текущий момент, но и в ретроспективе;
- формирование бизнес-модели. Создание единой версии правды (Single Version of Truth) для всей компании. Здесь фиксируются ключевые сущности бизнеса, их атрибуты и связи;
- обеспечение целостности. Ядро не подстраивается под запросы отдельных отделов, а отражает фундаментальную логику бизнеса, обеспечивая консистентность данных для всех аналитических процессов.

### 3.1. Data Vault 2.0 в ядре хранилища

**Data Vault 2.0** — методология построения ядра хранилища данных, основанная на трех основных компонентах:

| Компонент | Описание | Примеры в проекте |
|-----------|----------|-------------------|
| **Hubs** | Хранят бизнес-ключи и служат центром интеграции | `hub_customer`, `hub_order`, `hub_part`, `hub_supplier` |
| **Links** | Представляют отношения между хабами (бизнес-процессы) | `link_order_customer`, `link_order_lineitem` |
| **Satellites** | Хранят описательные атрибуты с отслеживанием истории | `sat_customer_details`, `sat_order_details`, `sat_lineitem_details`, `sat_part_details`, `sat_supplier_details` |

**Преимущества Data Vault 2.0:**
- **Гибкость**: добавление новых атрибутов без изменения ядра
- **Масштабируемость**: независимая загрузка компонентов
- **Аудитируемость**: полная история изменений с хеш-ключами

**Особенности реализации в ClickHouse:**
- `MergeTree()` движок для эффективного хранения
- `order_by` по хеш-ключам и датам загрузки
- `partition_by` по году загрузки
- Хеш-ключи: `MD5(business_key)` для hubs, `MD5(attr1 || attr2 || ...)` для hashdiff

## 4. Слой витрин данных (Data Marts)

Витрины данных — это тематические подмножества данных из ядра, созданные для конкретных бизнес-подразделений или задач (например, маркетинг, продажи, финансы).

**Функции:**

- оптимизация под задачи. Витрины структурированы таким образом, чтобы аналитикам не приходилось писать сложные запросы к огромному ядру. Они содержат уже агрегированные показатели и измерения, необходимые конкретной команде;
- повышение производительности: Запросы к витринам выполняются значительно быстрее, так как объем данных в них меньше и они денормализованы для скорости чтения.

*Пример:*
Витрина для отдела маркетинга может содержать данные о транзакциях клиентов: количество операций, средний чек, история отмен и т.д., что позволяет сразу работать с готовыми показателями без копания в сырых данных.

### 4.1. Витрины в проекте dbt-clickhouse-lab

| Витрина | Описание | Источник |
|---------|----------|----------|
| `f_lineorder_flat` | Широкая таблица для отчетности (star schema) | Прямое объединение staging таблиц |
| `f_lineorder_flat_dv` | Wide table для backward compatibility | Data Vault представление |
| `f_orders_stats` | Агрегированная статистика по заказам | Star schema |
| `f_orders_stats_dv` | Агрегированная статистика | Data Vault представление |

**Рекомендация:** Использовать Data Vault-based витрины (`*_dv`) для новых отчетов, так как они обеспечивают целостность и историзацию данных.

## 5. Слой семантики и метаданных

Этот слой обеспечивает «перевод» технических терминов на язык бизнеса и управление описанием данных.

**Функции:**

- бизнес-глоссарий. Создание единого словаря определений (например, что именно компания понимает под «доходом» или «активным пользователем»).
- управление метаданными. Хранение информации о структуре таблиц, типах данных, правилах трансформации и владельцах данных.
- Data Governance: Обеспечение качества данных (Data Quality) и управления мастер-данными (Master Data Management — MDM), что гарантирует точность и надежность аналитики.

### 5.1. Метаданные в dbt

dbt предоставляет встроенные механизмы для управления метаданными:

```yaml
# models/sources/sources.yml
sources:
  - name: dbgen
    description: "TPCH synthetic data stored in S3"
    tables:
      - name: orders
        description: "Orders facts"
        columns:
          - name: O_ORDERKEY
            description: "Unique order identifier"
            tests:
              - unique
              - not_null
```

## 6. Слой потребления (Reporting / BI Layer)

Финальный уровень архитектуры, с которым взаимодействуют конечные пользователи: аналитики, менеджеры и руководители.

**Функции:**

- визуализация. Построение дашбордов, отчетов и графиков с помощью BI-инструментов;
- доступ к данным. Предоставление интерфейсов ��ля выполнения ad-hoc запросов к витринам или ядру хранилища;
- self-service аналитика. Возможность для бизнес-пользователей самостоятельно исследовать данные без привлечения IT-специалистов.

## Практические рекомендации для проекта

### 1. Архитектурная диаграмма

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        Reporting / BI Layer                             │
│              (Tableau, Metabase, Redash, Custom Apps)                   │
└─────────────────────────────────────────────────────────────────────────┘
                                    ▲
                                    │
┌─────────────────────────────────────────────────────────────────────────┐
│                         Data Marts Layer                                │
│              f_orders_stats, f_lineorder_flat (DV-based)                │
└─────────────────────────────────────────────────────────────────────────┘
                                    ▲
                                    │
┌─────────────────────────────────────────────────────────────────────────┐
│                  Core Data Store (Data Vault 2.0)                       │
│   ┌─────────────┐  ┌─────────────┐  ┌───────────────────────────────┐   │
│   │   Hubs      │  │   Links     │  │      Satellites (history)     │   │
│   │ - customer  │  │ - orders    │  │ - customer_details            │   │
│   │ - order     │  │ - lineitem  │  │ - order_details               │   │
│   │ - part      │  │             │  │ - lineitem_details            │   │
│   │ - supplier  │  │             │  │ - part_details                │   │
│   └─────────────┘  └─────────────┘  │ - supplier_details            │   │
│                                      └───────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────┘
                                    ▲
                                    │
┌─────────────────────────────────────────────────────────────────────────┐
│                       Staging Area (ODS)                                │
│                    stg_customer, stg_orders, ...                        │
└─────────────────────────────────────────────────────────────────────────┘
                                    ▲
                                    │
┌─────────────────────────────────────────────────────────────────────────┐
│                      Source Layer (S3 TPCH)                             │
│                  src_customer, src_orders, src_lineitem, ...            │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2. Рекомендации по реализации

1. **Для новых проектов**: начинать с Data Vault 2.0 в ядре, затем создавать витрины поверх него
2. **Для существующих проектов**: постепенно мигрировать star schema модели на Data Vault
3. **Использование**: 
   - BI-системы → Data Marts (DV-based views)
   - Аналитики → Data Marts или direct access к satellites для детального анализа
   - Разработчики → Hubs и Links для построения сложных отчетов

### 3. Миграция с текущей архитектуры

Текущая реализация в проекте уже использует гибридный подход:

- **Staging** слой реализован через `stg_*.sql` модели
- **Data Vault** слой реализован через `hub_*.sql`, `link_*.sql`, `sat_*.sql` модели
- **Data Marts** слой реализован через `f_orders_stats`, `f_lineorder_flat` и их DV-версии

**Рекомендации по улучшению:**

1. Добавить документацию по каждому hub/link/satellite в `docs/` папке
2. Создать `semantic_layer/` с описанием бизнес-метрик
3. Добавить тесты для проверки целостности Data Vault
4. Создать materialized views для часто используемых Data Mart запросов
5. Документировать SLA для каждого слоя (время загрузки, актуальность данных)

### 4. Чек-лист для проверки архитектуры

- [ ] Все бизнес-ключи уникальны в hubs
- [ ] Links содержат только валидные ссылки на hubs
- [ ] Satellites хранят историю изменений
- [ ] Hashdiffы корректно вычисляются
- [ ] Data Marts используют Data Vault как источник
- [ ] BI-системы не имеют прямого доступа к сырым данным
- [ ] Метаданные документированы
